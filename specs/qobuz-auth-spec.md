# Qobuz Authentication Flow — Implementation Spec

> Backend component of `ostinato-radio`. This document specifies the complete authentication flow against the Qobuz API (unofficial, reverse-engineered) and is meant to be self-contained for an AI implementation agent.

## 1. Context

Qobuz has no official public API. The web player at `play.qobuz.com` uses an internal API exposed at `https://www.qobuz.com/api.json/0.2/`. As of April 2026, the legacy email/password login (`user/login` with MD5-hashed password) is broken and returns `401 User authentication is required`.

Qobuz has migrated its web player to a new OAuth 2.0 Authorization Code flow. This flow is **not officially documented** but has been reverse-engineered from network traces of the official web player. It works reliably and is the mechanism `ostinato-radio` must use.

This spec describes:
- How to scrape the three static credentials (`app_id`, `private_key`, `app_secret`) from the web player's JavaScript bundle
- How to drive the OAuth authorization code flow end-to-end
- How to obtain and use the resulting `user_auth_token`
- How to sign streaming URL requests using `app_secret`
- Error handling, refresh behavior, and reliability concerns

## 2. Constraints & Conventions

- The implementation language is **Rust** (the `ostinato-radio` backend is built on Axum + Tokio).
- All credentials and tokens are held **in memory only** — no database, no disk persistence beyond optional config.
- HTTP client: `reqwest` with `rustls-tls`. JSON: `serde_json`.
- The user authenticates from a browser. The PWA frontend opens the Qobuz signin URL; Qobuz redirects to a backend callback endpoint after successful authentication.
- The backend's callback URL must be reachable from the browser performing the login. Local IPs (e.g. `http://192.168.1.2:8080/auth/callback`) work — Qobuz does not validate the `redirect_url` parameter.

## 3. The Five Components of Authentication

### 3.1 `app_id`

- A static numeric identifier for the Qobuz web client application.
- Known current value: **`798273057`** (as of bundle version 8.1.0-b019).
- Embedded in `bundle.js`. Changes only when Qobuz deploys a new web player version.
- Required as the `ext_app_id` query parameter on the OAuth URL, and as the `X-App-Id` HTTP header on all API calls.

### 3.2 `private_key`

- A static alphanumeric string of ~12 characters used to exchange the OAuth `code_autorisation` for a `user_auth_token`.
- Known current value: **`6lz8C03UDIC7`** (as of bundle version 8.1.0-b019).
- Embedded in `bundle.js`. Changes only when Qobuz deploys a new web player version.
- Required as the `private_key` query parameter on the `oauth/callback` API call.

### 3.3 `app_secret`

- A static 32-character hexadecimal string (MD5-format) used to **sign streaming URL requests**.
- Example format: `abb21364945c0583309667d13ca3d93a`.
- Embedded in `bundle.js`, typically base64-encoded. Changes only when Qobuz deploys a new web player version.
- **Distinct from `private_key`** — these are two separate values serving two separate purposes. `private_key` is for OAuth token exchange only. `app_secret` is for request signing only.
- Required exclusively for `track/getFileUrl` calls (obtaining authenticated stream URLs). Not used in the OAuth flow.
- Historically, Qobuz embedded multiple candidate secrets in the bundle; only one validates correctly. The validation approach is described in §6.

**Signing formula for `track/getFileUrl`:**

```
request_ts  = current Unix timestamp (seconds)
request_sig = MD5(
    "trackgetFileUrl"         // object name + method name, concatenated
    + "format_id" + format_id // sorted parameter key+value pairs
    + "intentstream"
    + "track_id" + track_id
    + request_ts
    + app_secret
)
```

The full parameter concatenation order follows the Qobuz API convention: `object_name + method_name + sorted_params_concat + timestamp + app_secret`, where `sorted_params_concat` is all query parameter key-value pairs sorted alphabetically by key, concatenated without separators.

The resulting request:

```
GET https://www.qobuz.com/api.json/0.2/track/getFileUrl
    ?track_id={id}
    &format_id={format_id}
    &intent=stream
    &request_ts={timestamp}
    &request_sig={md5_hex}

Headers:
    X-App-Id:           {app_id}
    X-User-Auth-Token:  {user_auth_token}
```

`format_id` values: `5` = MP3 320kbps, `6` = FLAC 16-bit, `7` = FLAC 24-bit ≤96kHz, `27` = FLAC 24-bit Hi-Res (recommended).

### 3.4 `code_autorisation`

- A short-lived, single-use authorization code generated by Qobuz after successful user authentication.
- Returned as a query parameter on the redirect URL (`?code_autorisation=...`).
- Format: 8 alphanumeric characters (example: `1qpltn5e`, `19rPYCtF`).
- Must be exchanged for a `user_auth_token` immediately. Lifetime is short (assume <1 minute).

### 3.5 `user_auth_token`

- The persistent user session token. All authenticated API calls require it.
- Sent as the `X-User-Auth-Token` HTTP header on every API call.
- Lifetime: based on existing community implementations, valid for approximately 7 days before re-authentication is required.
- Treated as **highly sensitive** — must never be logged, persisted to disk, or returned to the frontend in plaintext.

## 4. Step-by-Step Flow

### Step 1 — Scrape `app_id`, `private_key`, and `app_secret` from `bundle.js`

On backend startup (and on demand if a later API call fails with `401`/`403`):

1. `GET https://play.qobuz.com/` — fetch the web player HTML.
2. Parse out the bundle path with the regex `/(/resources/[\d.]+-b\d+/bundle\.js)/`.
3. `GET https://play.qobuz.com{bundle_path}` — fetch the bundle JavaScript.
4. Search the bundle for `app_id`, `private_key`, and `app_secret`. The bundle is heavily minified and may be obfuscated; multiple regex patterns should be tried in sequence (see §6).

**Implementation note:** Because the bundle is minified, regex extraction is fragile. The implementation MUST:

- Try a sequence of candidate regex patterns for each value (see §6 for patterns).
- For `app_secret` specifically: the bundle typically embeds multiple candidate secrets. Each must be validated by attempting a real `track/getFileUrl` call to confirm the signature is accepted (see §7.4).
- Fall back to **configurable hardcoded values** read from environment variables `QOBUZ_APP_ID`, `QOBUZ_PRIVATE_KEY`, and `QOBUZ_APP_SECRET` if scraping fails.
- Log clearly which path was used (scraped vs. fallback).
- Cache scraped values in memory for the lifetime of the process. Re-scrape only on validation failure.

### Step 2 — Build the OAuth URL and serve it to the PWA

The backend exposes an endpoint:

```
GET /auth/start
```

Response:

```json
{
  "oauth_url": "https://www.qobuz.com/signin/oauth?ext_app_id=798273057&redirect_url=http%3A%2F%2F192.168.1.2%3A8080%2Fauth%2Fcallback"
}
```

The PWA opens this URL in a new browser tab/window. The `redirect_url` value is the backend's public callback endpoint and must be URL-encoded.

The `redirect_url` is constructed from the backend's `public_base_url` configuration (see `ostinato-radio` main spec §6).

### Step 3 — User authenticates on Qobuz

This happens entirely outside the backend's reach. The user logs in on `www.qobuz.com`. On success, Qobuz issues a 302 redirect to the configured `redirect_url` with `?code_autorisation=XXXX` appended.

### Step 4 — Backend captures the code

```
GET /auth/callback?code_autorisation={code}
```

Handler logic:

1. Read `code_autorisation` from the query string.
2. If missing, return a 400 with a user-facing HTML error page.
3. Immediately exchange the code for a token (next step). Do NOT redirect the browser yet.
4. On success: respond with a small HTML page that says "Authentication successful — you can close this tab" and uses JavaScript `window.close()` (best-effort).

### Step 5 — Exchange code for token

```
GET https://www.qobuz.com/api.json/0.2/oauth/callback
    ?code={code_autorisation}
    &private_key={private_key}

Headers:
    X-App-Id: {app_id}
    Origin:   https://play.qobuz.com
    Referer:  https://play.qobuz.com/
    User-Agent: <a reasonable browser-like UA>
```

Expected response:

```json
{
  "token":   "xbNDimm0n5F0...",
  "user_id": "1149746"
}
```

On any non-200 response, treat as authentication failure. If the response status is 401 or the body contains `{"code": 401, ...}`, **invalidate the cached `app_id` and `private_key` and re-scrape** before failing the operation.

### Step 6 — Confirm and enrich with `user/login`

After receiving the token, immediately call:

```
POST https://www.qobuz.com/api.json/0.2/user/login

Headers:
    X-App-Id:           {app_id}
    X-User-Auth-Token:  {token}
    Origin:             https://play.qobuz.com
    Referer:            https://play.qobuz.com/
    Content-Type:       application/x-www-form-urlencoded

Body:
    extra=partner
```

Expected response includes the full user profile (display name, email, country, subscription details, etc.). This call serves two purposes:

1. Confirms the token actually works on a regular authenticated endpoint.
2. Provides the user profile for the frontend to display.

Store the relevant profile fields in memory:

```rust
pub struct QobuzCredentials {
    pub app_id:      String,
    pub private_key: String,
    pub app_secret:  String,    // sensitive — used for request signing
}

pub struct QobuzSession {
    pub credentials:  QobuzCredentials,
    pub user_id:      String,
    pub auth_token:   String,    // sensitive
    pub display_name: String,
    pub email:        String,
    pub country_code: String,
    pub subscription: Option<String>, // e.g. "studio"
    pub obtained_at:  Instant,
}
```

### Step 7 — Notify the PWA

The PWA polls a backend endpoint to know when authentication completes:

```
GET /auth/status

Response:
  - 200 with profile JSON if authenticated
  - 401 if not authenticated yet
```

Alternative: a server-sent event or WebSocket. SSE is preferred for simplicity. Either approach is acceptable.

The PWA never receives the `auth_token` — it only sees public-safe profile fields.

## 6. Bundle Scraping Patterns

The bundle is JavaScript, minified. Patterns must be regex-based and tried in sequence. Candidate patterns:

For `app_id` (a 7-10 digit number near related identifiers):

```regex
ext_app_id["\s:=,]+(\d{7,10})
app_id["\s:=,]+["'](\d{7,10})["']
"appId"\s*:\s*"(\d{7,10})"
appId\s*=\s*["'](\d{7,10})["']
```

For `private_key` (alphanumeric string near `private_key`):

```regex
private_key["\s:=,]+["']([A-Za-z0-9]{8,20})["']
"privateKey"\s*:\s*"([A-Za-z0-9]{8,20})"
privateKey\s*=\s*["']([A-Za-z0-9]{8,20})["']
```

For `app_secret` (32-char hex string, possibly base64-encoded in the bundle):

```regex
[a-f0-9]{32}
```

The bundle historically contains multiple 32-char hex candidates. All must be collected and validated. Validation: construct a signed `track/getFileUrl` request for a known public track ID and check the response is not `{"code": 401, ...}`. The first candidate that produces a valid response is the correct `app_secret`.

If the secrets are base64-encoded in the bundle (common in older versions), decode each candidate before validation:

```regex
["']([A-Za-z0-9+/]{44,48}={0,2})["']   // base64-encoded 32-byte value
```

**Important:** these patterns are unreliable against arbitrary minification. The implementation should:

1. Try all patterns.
2. Validate each candidate by attempting a real `oauth/callback` exchange against a known-good code, OR by checking that the format is plausible (right length, right character class).
3. Fall back to environment-configured values if no candidate validates.
4. Log a clear warning if fallback is used so the operator can update the regex.

## 7. Error Handling

### 7.1 Network errors during bundle fetch

Retry with exponential backoff (3 attempts: 0s, 1s, 3s). If all fail, return a clear error and use fallback values from environment.

### 7.2 `oauth/callback` returns 401/403

Two possible causes:

- The `code_autorisation` expired or was already consumed → user must retry the entire flow.
- The `private_key` is stale (Qobuz updated the bundle) → invalidate cached credentials, re-scrape, and retry once.

Distinguish these by attempting a re-scrape: if the scraped `private_key` differs from the cached one, the second case is confirmed.

### 7.3 `user/login` returns 401

The `user_auth_token` is invalid (expired or revoked). Clear the session in memory; the PWA must trigger a fresh `/auth/start`.

### 7.4 Validating scraped credentials

**`private_key`**: no standalone validation possible without a fresh `code_autorisation`. Assume valid until an `oauth/callback` call fails, then re-scrape.

**`app_secret`**: validate by attempting a signed `track/getFileUrl` call against a known public track. Use a short, publicly available track ID (hardcode one in the implementation as a canary). If the response is 200 with a `url` field, the secret is valid. If 401, try the next candidate. If all candidates fail, fall back to the environment variable `QOBUZ_APP_SECRET`.

### 7.5 Rate limiting

If the API ever returns `429`, back off for at least 60 seconds and surface the error. Do not retry aggressively.

## 8. Security Requirements

- `user_auth_token` MUST NOT be:
  - Logged at any level
  - Written to disk
  - Included in error messages returned to the PWA
  - Returned to the PWA in API responses (except optionally as an opaque session ID)
- Sensitive fields MUST be redacted in logs: `token`, `auth_token`, `user_auth_token`, `app_secret`, `private_key`, `password`, `secret`, `request_sig`.
- The backend's `/auth/callback` endpoint MUST NOT be CSRF-protected via a referer check (Qobuz is the legitimate cross-origin caller). It should however validate that `code_autorisation` is well-formed (alphanumeric, 6-12 chars) before forwarding.
- All outbound HTTP calls to Qobuz MUST use HTTPS. Reject any redirect to HTTP.
- The PWA-facing endpoints MUST be served over HTTPS in production. During local development, HTTP on the LAN is acceptable.

## 9. Configuration

```toml
[qobuz]
# Fallback static values used if bundle scraping fails.
# Updated manually when Qobuz changes the bundle.
fallback_app_id      = "798273057"
fallback_private_key = "6lz8C03UDIC7"
fallback_app_secret  = ""   # leave empty; set via QOBUZ_APP_SECRET env var

# How often to re-scrape proactively (in addition to on-failure refresh).
# Set to 0 to disable proactive refresh.
scrape_refresh_hours = 24
```

Environment variable overrides:

- `QOBUZ_APP_ID`
- `QOBUZ_PRIVATE_KEY`
- `QOBUZ_APP_SECRET`

These take precedence over the TOML values and over scraped values. Use only for emergency overrides.

## 10. HTTP Endpoints Exposed by the Backend

| Method | Path                  | Purpose                                                     |
|--------|-----------------------|-------------------------------------------------------------|
| GET    | `/auth/start`         | Returns the OAuth URL for the PWA to open                   |
| GET    | `/auth/callback`      | Receives the redirect from Qobuz, exchanges code for token  |
| GET    | `/auth/status`        | Returns current auth state and (safe) profile fields        |
| POST   | `/auth/logout`        | Clears the in-memory session                                |

All except `/auth/callback` require a PWA session cookie (separate from Qobuz auth — see main spec §8).

## 11. End-to-End Validation (Reference Test)

The reference Python script that validated this flow (`test_qobuz_flow.py`) demonstrates the complete sequence works against the live Qobuz API. The Rust implementation MUST produce the same observable behavior:

1. Scrape (or fall back) → obtain `app_id`, `private_key`, and `app_secret`
2. Validate `app_secret` via a signed `track/getFileUrl` canary call
3. Start local server on configured callback port
4. Construct OAuth URL with PWA-friendly `redirect_url`
5. On redirect, capture `code_autorisation`
6. Exchange via `oauth/callback` → receive `{ token, user_id }`
7. Confirm via `user/login` with `extra=partner` → receive full profile

Implementations SHOULD include integration tests that mock the Qobuz endpoints and walk through this sequence.

## 12. Known Fragility & Mitigation

| Risk                                            | Mitigation                                                          |
|-------------------------------------------------|---------------------------------------------------------------------|
| Qobuz changes `app_id`, `private_key`, or `app_secret` | Re-scrape on auth failure; fallback to env vars; clear logging  |
| Qobuz minification breaks regex patterns        | Multiple patterns tried in sequence; fallback to env vars           |
| Qobuz changes the OAuth flow shape              | Re-capture HAR from `play.qobuz.com`; update flow spec              |
| Qobuz changes the bundle URL format             | Update the regex in §6                                              |
| Token revoked mid-session                       | Detect 401 on any API call, clear session, prompt re-auth           |
| Qobuz adds redirect_url validation              | Switch to a publicly-reachable callback URL                         |

## 13. Out of Scope

- Refreshing the `user_auth_token` without user interaction. There is no known refresh-token mechanism in this flow. When the token expires, the user must re-authenticate via the OAuth flow.
- Storing or restoring sessions across backend restarts. The token is in-memory only.
- Supporting more than one Qobuz user simultaneously. This is a single-user, self-hosted system.
- Bypassing region restrictions or accessing content the user is not entitled to.

## 14. Disclaimer

This authentication flow is based on reverse engineering of publicly-served JavaScript and observed network traffic. It is not endorsed, certified, or otherwise approved by Qobuz. The implementation accesses only data the authenticated user is entitled to via their own Qobuz subscription. No private secrets are redistributed; `app_id`, `private_key`, and `app_secret` are scraped at runtime from publicly available client-side code, consistent with prior open-source projects (Navidrome, Strawberry, streamrip, qobuz-dl).
